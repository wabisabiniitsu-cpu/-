## 3. 推奨アーキテクチャ

### 3-1. 構成概要

```
[従業員スマホ] ──HTTPS──▶ 予約アプリ（Netlify・別サイト）
[RELI管理者]   ──HTTPS──▶   ├ 画面：Next.js（SSR、noindex）
                             ├ API ：Next.js Route Handlers（サーバー側でのみDB・メールにアクセス）
                             └ 定期処理：Netlify Scheduled Functions（毎分〜5分）
                                   ├ 期限切れhold解放
                                   ├ メール送信キュー（outbox）処理・再試行
                                   └ リマインド送信
                      ▼                         ▼
             PostgreSQL（Neon）           メール配信（Resend 推奨）
```

- **既存サイトとは別リポジトリ・別Netlifyサイト**にする（既存の破壊的変更を避け、Cookie・認証境界も分離）
- 公開URLは独自ドメイン取得後に `book.<独自ドメイン>` を推奨。取得前のテストは `reli-booking.netlify.app` 等
- 公式サイト・LPからは予約アプリへリンクしない（企業担当者にだけ専用URL/QRを渡す）

## 4. 設計

### 4-1. 状態遷移

**訪問（visits.status）** — 予約ステータスとは別フィールド

| 現在 → 次 | 操作者 | 備考 |
|---|---|---|
| draft → accepting | 管理者 | 枠・受付期間が設定済みであること |
| accepting → closed_accepting | 管理者 / 受付締切到達 | 予約受付停止（訪問判断前） |
| closed_accepting → accepting | 管理者 | 受付再開 |
| accepting / closed_accepting → confirmed | **管理者のみ** | 確定予約者へ「訪問実施確定」メール |
| accepting / closed_accepting / confirmed → cancelled | **管理者のみ** | 確定予約者へ「訪問中止」メール。予約は `cancelled_by_visit` に |
| confirmed → completed | 管理者 | 訪問日以降のみ |
| 上記以外（逆行・cancelled/completed からの遷移） | — | 不可（DBとAPIの両方で拒否） |

**予約（reservations.status）**

| 現在 → 次 | きっかけ |
|---|---|
| （新規）→ pending_email_verification | フォーム送信。枠をhold |
| pending → confirmed | 期限内のメール認証成功 |
| pending → expired | 10分経過（定期処理 or 次の予約処理時に解放） |
| confirmed → cancelled | 本人 or 管理者のキャンセル |
| confirmed → cancelled_by_visit | 訪問中止 |
| confirmed → completed | 訪問完了処理 |
| confirmed → confirmed（枠変更） | 変更は「新予約作成＋旧予約キャンセル」を1トランザクションで実施し、履歴を残す |

### 4-2. hold の提案（Q5で承認が必要）

- **開始**：氏名・メール送信時。予約を `pending_email_verification` で作成し、`hold_expires_at = 送信時刻 + 10分`（認証トークン期限と同一）
- **確定**：認証リンクを開き「予約を確定する」ボタン押下時に、hold期限内かつトークン未使用なら確定（メールソフトのリンク先読みで誤確定しないよう、リンクを開くだけでは確定しない）
- **期限切れ**：
  - 公開APIの空き枠計算は `confirmed` と「期限内の pending」だけを埋まりとみなす（定期処理が遅れても枠は解放されて見える）
  - 同じ枠に新規予約が来たら、トランザクション内で期限切れpendingを `expired` に更新してから確保
  - 定期処理でも5分ごとに一括 `expired` 化
- **期限切れ後**：「確認の有効期限が切れました。お手数ですが最初からお申し込みください」＋同じ企業ページへのボタン。枠が残っていれば再予約可
- **認証メール再送**：同じ予約に対して最大2回、各回でトークンを作り直し旧トークンを無効化。**hold期限は延長しない**（要確認）

### 4-3. 二重予約防止（DBレベル）

- `slots` 行を `SELECT ... FOR UPDATE` でロックしてから判定
- 部分一意インデックス：`UNIQUE (slot_id) WHERE status IN ('pending_email_verification','confirmed')`
- 同一人物の重複（ルール確定後）：例「同一訪問日1件まで」なら `UNIQUE (visit_id, email_normalized) WHERE status IN (...)`

### 4-4. ユニーク確定予約者数と6名境界通知

- 人数 = 対象訪問の `confirmed` 予約の `email_normalized` の重複なし件数（判定規則はQ6で確定）
- `visits.threshold_reached`（bool）を保持。予約確定・変更・キャンセルの同一トランザクション内で再計算し、**false→true / true→false が変わった時だけ**管理者向け通知イベントを outbox に書く
- 基準値（6）は `admin_settings` テーブルに保存。公開用のコード・API・HTMLには含めない
- 変化しても訪問状態は一切変更しない

### 4-5. データモデル（概略）

| テーブル | 主な項目 |
|---|---|
| companies | id, name, display_name（公開用表示名）, status, created_at |
| company_booking_links | id, company_id, token_hash, status(active/revoked), expires_at, created_at, revoked_at |
| visits | id, company_id, visit_date, status, accept_from, accept_until, threshold_reached, confirmed_at/by, cancelled_at/by, notes(内部) |
| slots | id, visit_id, starts_at(UTC), ends_at(UTC), blocked(bool), UNIQUE(visit_id, starts_at) |
| reservations | id, visit_id, slot_id, name, email, email_normalized, status, hold_expires_at, confirmed_at, cancelled_at, replaced_by, consent_version, created_at |
| email_verifications | id, reservation_id, token_hash, expires_at, used_at, sent_count |
| reservation_access_tokens | id, reservation_id, token_hash, purpose(manage), expires_at, revoked_at |
| admin_users | id, email, password_hash(argon2id), totp_secret(暗号化), status, last_login_at |

### 4-7. 画面構成

**従業員**：企業予約ページ（日付→空き枠選択）→ 氏名・メール・同意入力 → 「確認メールを送信しました」→ メールのリンク → 確定ボタン → 予約受付完了 → 予約確認・変更・キャンセルページ

**表示文言の原則**：予約受付完了画面は「ご予約を受け付けました。訪問の実施については、RELIが予約状況を確認のうえ改めてご案内します」。人数・進捗バー・「あと○名」は一切出さない。

### 4-9. 通知の送信設計

- すべて outbox（notification_events）経由。`event_key` 例：`visit:{id}:confirmed:{reservationId}` で同一メールの二重送信を防止
- 訪問確定・中止は、ボタン押下時点の確定予約者全員に1通ずつイベント生成 → 順次送信。失敗分は自動再試行（最大5回・間隔を延ばす）→ それでも失敗なら管理画面に「未送信あり」表示＋手動再送ボタン＋管理者へ異常メール
- 確定後に新規予約した人へは、予約確定メールの文面を「訪問実施が決定している日」用に切り替える
